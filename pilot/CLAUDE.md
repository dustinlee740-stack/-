# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Workspace 범위

이 CLAUDE.md는 **D:\da\pilot 한 폴더에만** 적용된다. 부모 `D:\da` 아래의 다른 폴더(v1/, query_diff/, tests/, ttp_workflow/ 및 build_components_xlsx.py, standardize_descriptions.py 등)는 별개 워크스페이스로 취급한다 — 읽거나 참조하지 말 것.

## Purpose

이 워크스페이스는 코나카드(Konacard) 컴포넌트 카탈로그(`components.xlsx`, 208개)를 다루는 세 가지 도구를 제공한다.

1. **변환 (xlsx → md)** — 카탈로그를 사람이 읽기 좋은 `components.md`로 변환.
2. **영향 범위 체크 (요건 → 후보 컴포넌트)** — 새 요건이 들어왔을 때, 그 요건을 구현·수정하려면 손대야 할 컴포넌트 후보를 추천.
3. **워크숍 자료 빌더 (보조)** — `docs/make_pilot_overview.py`로 도구 개요 PPT(`docs/pilot_overview.pptx`)를 결정론적으로 생성.

## Common commands

```bash
# 변환 (xlsx -> md)
python xlsx_to_md.py

# 영향 분석 머티리얼 갱신 (components.xlsx 변경 시 재실행)
python impact.py

# 의존성 (필요 시)
pip install pandas openpyxl
```

빌드/린트/테스트 도구는 이 워크스페이스에 구성되어 있지 않다.

## 변환 (xlsx_to_md.py)

- 입력 `components.xlsx` — 컬럼: `Name`, `Full Name`, `대분류`(또는 `Major Categories`), `중분류`(또는 `Medium Category`), `소분류`(또는 `Subcategories`), `Korean Description`, `English Description`. 한/영 헤더 모두 허용 (`pick()` at xlsx_to_md.py:25).
- 변환 스크립트 `xlsx_to_md.py`
  - `slugify()` (xlsx_to_md.py:32) — 한글/영숫자/하이픈만 남기는 GitHub 호환 슬러그
  - `main()` (xlsx_to_md.py:48) — Name 기준 정렬 → 대/중분류로 그룹핑(첫 등장 순서 유지) → TOC + 컴포넌트 상세 섹션 출력
- 출력 `components.md` — 헤더(통계) + 목차(대>중>컴포넌트 링크) + 컴포넌트별 상세(분류 breadcrumb, 한/영 설명 코드블록).

`components.md`는 **자동 생성물이므로 직접 편집하지 말 것**. 내용을 바꾸려면 `components.xlsx`를 갱신한 뒤 스크립트를 재실행한다.

## 영향 범위 체크 (impact 워크플로우)

### 시나리오 (중요)

입력은 **요건 설명서 파일**(.txt/.md), 출력은 그 요건을 구현·수정하려면 손대야 할 **영향 가능한 모든 컴포넌트**(분류별 그룹).

- **변경→영향 역추적이 아니다** — 의존성 그래프를 만들거나 사용하지 않는다. `Depends On` 같은 컬럼도 사용하지 않는다.
- **TOP-N 컷 없음** — recall 우선. 영향 가능성이 있는 컴포넌트는 빠뜨리지 않고 모두 도출한다.
- **부분문자열 매칭이 아니다** — 추론 단계는 의미 비교가 필요하므로 Claude Code가 직접 수행한다.

### 책임 분담

| 단계 | 주체 | 산출물 |
| --- | --- | --- |
| 머티리얼 생성 | `impact.py` (결정론적, LLM 호출 없음) | `impact_context.md` |
| 분류 도출 (1단계) | Claude Code (이 도구) | 추론 단계와 통합 |
| 비교·추론 (2단계) | Claude Code (이 도구) | 결과 md + jsonl 로그 |

### 워크플로우 (Claude Code가 사용자 요청을 받으면 수행)

사용자가 "영향 분석해줘 reqs/X.md" 같은 요청을 하면 다음 절차로 진행한다.

1. **머티리얼 freshness 확인**: `impact_context.md`가 없거나 `components.xlsx`보다 오래되면 `python impact.py`를 먼저 실행한다(머티리얼 갱신).
2. **자료 로딩**: 요건 파일과 `impact_context.md`를 읽는다. 비교·추론 단계에서 추가 정보가 필요하면 `components.md`로 컴포넌트 전문 설명을 참조한다.
3. **분류 도출 (1단계)**: 요건 본문을 읽고 관련 가능성이 있는 대/중/소분류 후보를 도출한다. 빠뜨림 방지를 위해 보수적으로 폭넓게 잡는다 — 애매하면 포함시킨다.
4. **비교·추론 (2단계)**: 도출된 분류 안의 모든 컴포넌트에 대해, 컴포넌트의 설명·연계 정보와 요건 내용을 비교·추론하여 영향 가능성을 판단한다. 영향 가능한 모든 컴포넌트를 도출한다(TOP-N 컷 없음). 각 항목에 대해 영향 사유를 1~2문장으로 적는다.
5. **결과 저장**: `impact_<요건파일베이스>.md`로 결과를 작성(아래 형식 참조).
6. **로그 append**: `impact_log.jsonl`에 한 줄 추가(아래 형식 참조).

### 산출물 형식 표준

`impact_<basename>.md` (Claude Code가 작성):
- 헤더: 요건 파일 경로, 분석 시각(ISO), 도출된 분류 수, 영향 컴포넌트 수
- (선택) 요건 ID 기준 **flat 인덱스** 표 — `요건ID | 요건 이름 | Name | Full Name | 영향 사유 | components.md 링크`. 본문 분류별 표의 축약본으로 한 눈 스캔용. 본문(분류별 표)이 진실의 원천. E-XX 행에는 #10 추론 가이드라인의 작업 유형(A 검증/B 에러처리/C 로직검토/D 신규룰)을 사유에 명시.
- "## 도출된 분류": 대>중>소 트리 형태로, 각 분류별 도출 사유 1줄
- "## 영향 컴포넌트": 분류별 그룹. 그룹 안에 표 — `Name | Full Name | 영향 사유 | components.md 링크`
- "## 검토 메모(선택)": 분류는 도출됐으나 영향 없음으로 판정한 컴포넌트의 누락 사유

`impact_log.jsonl` (Claude Code가 한 줄 append):
- 라인 종류는 `entry_type` 키로 명시한다. 허용값: `new`(신규, impacted 단일 키), `new_split`(신규, impacted_primary/secondary 분리), `correction`(정정), `reverification`(재검증).
- 정정·재검증 라인은 `correction_of`/`reverification_of`(이전 라인 ts) + 카운트 키(`impacted_total_count` 또는 `impacted_primary_count`/`impacted_secondary_count`) 중 하나 이상을 포함한다.
- 기존 라인(entry_type 도입 전)은 검증기가 키셋으로 fallback 추론하므로 마이그레이션 불필요. 신규 라인부터 `entry_type` 사용.
```json
{"ts":"<ISO>","entry_type":"new","requirement_file":"<absolute path>","derived_categories":["대>중>소", ...],"impacted":[{"name":"IAS","reason":"..."}],"summary":"<1~2문장 요약>"}
```

### 도구

`impact.py`:
- 역할: `components.xlsx`를 읽어 추론 친화적 머티리얼 `impact_context.md`(분류 트리 + 컴포넌트별 한 줄 요약, 100자 cap)를 생성. 그 외 아무 일도 하지 않는다.
- 호출 시점: `components.xlsx`가 갱신될 때마다, 또는 워크플로우 1단계에서 freshness 확인 후 필요 시.
- 재사용: `pick()`(xlsx_to_md.py:25)을 import.

### 추론 가이드라인 (영향 판정 시 반드시 적용)

비교·추론 2단계에서 **"흐름에 등장하는가"가 아니라 "변경의 주체인가"**를 묻는 것이 핵심이다. 카탈로그 어휘에 매칭된다고 영향 컴포넌트로 잡으면 false positive가 폭증하고, "변경 없음" 분류라고 검토 메모로 보내면 검증·처리 작업이 누락되어 false negative가 생긴다. 다음 패턴을 명시 적용한다 — **#1~#9는 false positive 가드, #10은 false negative 가드**.

**1. 정책 본체는 KOD에 있다 — 원장은 정책 적용 결과를 적재할 뿐 (예외: 외부 솔루션 보유 정책)**
- 본 워크스페이스의 핵심 원칙: **대부분의 정책(한도/수수료/우선순위/할인 등)은 KOD_ITN(내부) / KOD_ETN(외부)가 들고 있다.** 도메인 원장은 KOD 정책을 받아 *적용한 결과를 적재*할 뿐 정책 자체의 본체가 아니다.
- 정책 변경 요건의 **1차 영향**은 거의 항상 KOD_ITN/KOD_ETN. **2차 영향**은 정책을 받아 검증·집행하는 도메인 원장(IAS/CS/RS/CMS).
- "정책이 바뀌면 원장이 영향" 사고는 결과적으로는 맞지만 *주체*는 KOD다. 산출물 사유에 "KOD 정책 변경" → "원장(예: CS)이 새 정책을 받아 적용" 관계로 명시할 것.
- **예외: 외부 솔루션이 정책을 가지는 도메인** — 일부 도메인의 정책은 외부 솔루션이 본체로 들고 있다. 본 워크스페이스에서 확인된 예외:
  - **AML 탐지 기준은 외부 솔루션 A-Safe가 본체** (KOD 아님). **AMLS**는 A-Safe ↔ 코나 *중재 어댑터*.
  - **이상탐지 룰은 KOD가 본체 아님 — FDS/KFDS가 역할 분담**:
    - **FDS** = **기존 이상탐지 수행, 룰 추가 불가** (read-only 적용자). 신규 룰이 필요한 요건이면 FDS는 변경 주체가 아니므로 영향 아님.
    - **KFDS** = **신규 이상탐지 룰의 본체이자 수행자** (룰 추가 + 수행 둘 다). 신규 이상탐지가 필요한 요건은 KFDS가 1차 영향.
    - 카탈로그상 KFDS 설명 "A-safe 대체 신규 FDS"는 outdated/오류이지만 사용자 결정으로 카탈로그 유지.
  - **쿠폰 정책은 KCPS(KonaCard 쿠폰 시스템)가 본체** (KOD 아님). 쿠폰 정책 변경 요건의 1차 영향은 KCPS, KOD가 아님.
  - 외부 솔루션(A-Safe)은 우리 카탈로그에 등장하지 않으므로 영향 컴포넌트 표에 직접 들어가지 않지만, 산출물 사유에 외부 본체 존재를 명시하고 중재 어댑터·적용자 컴포넌트의 영향만 표에 포함.
  - 다른 외부 솔루션 의존 도메인이 발견되면 같은 원칙으로 분리: 정책 본체(외부) → 중재 어댑터(코나) → 적용자(코나).

**2. 도메인별 원장(本)을 식별하라**
- **결제 도메인**의 원장: **IAS** (Issuer Authorization System) — 결제·승인·지불 거래 원장
- **환불 도메인**의 원장: **RS** (Refund Service) — 환불 본체. IAS와 별개. 환불 정책 변경 시 IAS는 raw data 적재만 받음(직접 영향 아님).
- **충전 도메인**의 원장: **CS** (Charge Service) — 충전 검증·누적 조회·자동충전 클라이언트. KOD 정책을 적용.
- **카드 도메인**의 원장: **CMS** (Card Management System) — 카드 라이프사이클·PAN.
- 한 도메인의 정책 변경 영향은 그 도메인 원장에 집중되며, **다른 도메인 원장은 데이터 적재만 받을 뿐 영향 아님** (예: 충전 한도 변경 시 IAS는 raw data 적재만 → 영향 없음. 환불 정책 변경 시 IAS는 거래 정보만 제공 → 영향 없음).

**3. By-pass 라우팅과 정책 본체를 구분하라**
- API Response를 그대로 통과시키는 라우팅 계층은 정책값이 바뀌어도 자체 변경되지 않는다.
- 대표 by-pass 컴포넌트: **PP, VVAN, EGS, BGS** (충전·결제 흐름에서 라우팅·검증을 담당하지만 정책은 KOD가, 적용은 원장이 함)
- "흐름이 통과한다 = 영향" 아님. 라우팅 컴포넌트 자체의 코드/설정 변경이 필요한지 물어야 함.

**4. "호출됨" vs "변경됨"을 구분하라**
- 충전·결제·환불 시 카드 상태 조회를 위해 CMS/DCP를, 회원 상태 조회를 위해 MAP을 호출한다. 그러나 한도·환불 정책이 바뀌어도 이들 컴포넌트 자체에 변경 요구가 없으면 영향 아님.
- 호출자(예: CS, RS)가 정책을 받아 적용하고, 호출되는 측은 단순 조회 응답만 한다 → 호출자만 영향, 호출되는 측은 영향 아님.

**5. 인증 실행 vs 인증 결과 조회**
- NICE-CORE, NCS, CVS, UIS는 본인인증을 *실행*하는 컴포넌트다.
- 한도·환불 정책이 "본인인증 완료 사용자"를 분기 조건으로 쓴다면, 이는 인증 결과를 *조회*할 뿐이며 인증 실행 자체는 변경되지 않는다 → 인증 컴포넌트는 영향 없음.
- 카탈로그에 "충전한도 상향 시 사용" 같은 문구가 있어도, 그것이 "한도값 변경 시"가 아니라 "한도 상향 권한을 얻기 위해 인증할 때"를 의미하는지 따져봐야 한다.

**6. 통계/집계는 원장 데이터 의존이다**
- SAS, CBSS, TBOSB 같은 통계·집계 컴포넌트는 원장 데이터를 받아 적재할 뿐, 정책 변경 자체로는 변경되지 않는다.
- 통계 정책 변경(예: 새 지표 추가, 새 차원 추가)이 *명시적으로 요건에 포함*된 경우에만 영향. "통계가 변할 것이다"는 자연스러운 결과로, 별도 요건으로 다룬다.

**7. 인프라 일반론은 영향 아님**
- KAFKA(메시징), SCC(설정 관리), KMS(키 관리), AGS(인증 게이트웨이), KAS(주소 검색) 같은 인프라는 정책 변경의 *직접 영향*을 받지 않는다.
- 메시지 흐름이 *새로 추가되거나*, 설정이 *해당 컴포넌트가 관리하는 것이거나*, 키 정책이 *변경되는* 경우에만 영향.

**8. 운영 데스크 짝(KOD_ITN ↔ KOD_ETN)을 함께 검토하라**
- 정책 등록/관리 관련 영향이면 내부용(KOD_ITN)만 보지 말고 외부용(KOD_ETN)도 함께 확인. 둘 다 정책 정보 제공 컴포넌트다.
- 다른 짝 쌍이 등장하면(예: 챗봇 코어/프론트, 알림 본체/라우팅) 동일 원칙으로 함께 검토.

**9. 카탈로그 어휘 직접 매칭은 함정 가능성 — 의미를 한 단계 더 풀어라**
- 카탈로그 설명의 단어가 요건 단어와 표면적으로 일치해도, 그것이 본 요건의 *변경 행위*에 해당하는지를 따로 판단해야 한다.
- 예: CVS 카탈로그 "충전한도 상향 시 사용"이라는 문구가 *어떤 시점에 무엇을 위해* 사용되는지 풀어보면 본 요건과 무관할 수 있다.

**10. 명시 제외 케이스(E-XX "변경 없음")는 "영향 없음"이 아니라 검증·처리 작업 — false negative 가드**
- #1~#9가 false positive 가드라면, 본 항은 *false negative* 가드. 카탈로그상 "예외 처리 유지/변경 없음"으로 분류되는 E-XX 엣지 케이스를 그대로 검토 메모로 보내면 *검증 작업·처리 로직 누락*이 발생한다.
- 매 E-XX마다 묻는다: **"이 케이스를 처리·검증하려면 어디에 작업이 필요한가?"** 카탈로그 흐름 매칭이 아니라 요건의 *작업 분량 도출* 관점.
- 작업 유형별 매핑:
  - **유형 A — 기존 정책 유지 검증**: "변경 적용 제외" 분기가 새 한도/룰에 휘말리지 않는지 확인. **정책 본체(KOD_ITN/KOD_ETN) + 도메인 원장(IAS/CS/RS/CMS) 모두 검증 대상에 포함**. (예: SP_001 E-01 미성년자, E-02 미인증, E-03 법인 — 한도 분기 유지 검증)
  - **유형 B — 차단·안내 에러 처리 추가**: 한도 소진/잔액 초과 같은 케이스 → 도메인 원장에 차단 안내 에러 메시지·플로우 추가. (예: SP_001 E-04 당일 한도 소진 후)
  - **유형 C — 경계 조건 로직 검토**: 자정 초기화/부분 처리 같은 경계 → 도메인 원장 + 안내·표시 컴포넌트(PCSI/DDA). (예: SP_001 E-05 자정 초기화, E-06 잔액 초과 부분 충전)
  - **유형 D — 신규 탐지 룰 추가**: PEP/이상 패턴 → 룰 본체(KFDS, AMLS 어댑터)에 신규 룰 추가. (예: SP_001 E-07 PEP 고객, E-10 분할 충전)
- 산출물 반영 규칙:
  - flat 인덱스: E-XX 행에 작업 유형 명시(검증 필요/에러 처리 추가/로직 검토/룰 추가).
  - 본문 분류별 표: 해당 컴포넌트 사유에 "**추가**: E-XX ..." 형태로 보강.
  - 검토 메모 "명시 제외 케이스" 절에는 *검증 작업조차 필요 없는* 진짜 무관 케이스만 남긴다. "변경 없음"이라는 이유만으로 명시 제외에 버리지 말 것.

## 도메인 메모

- **IAS vs CMS vs RS vs CS — 도메인 원장 매핑** — 결제·승인의 원장은 **IAS**, 카드 라이프사이클 원장은 **CMS**(PAN/기명화 등), 환불의 원장은 **RS**(IAS 아님), 충전의 원장은 **CS**. 위키 표현이 둘을 혼동시킬 수 있고, 한 도메인의 정책 변경 영향은 그 도메인 원장에만 집중된다(다른 원장은 raw data 적재만).
- **대부분의 정책의 본체는 KOD에 있다 (예외: 외부 솔루션, 이상탐지, 쿠폰)** — 한도/수수료/우선순위/할인 등 대부분의 정책은 **KOD_ITN(내부용) / KOD_ETN(외부용)**가 들고 있다. 도메인 원장(IAS/CS/RS/CMS)은 KOD 정책을 받아 *적용한 결과를 적재*할 뿐, 정책 자체의 본체가 아니다. 정책 변경 요건의 1차 영향은 KOD, 2차 영향은 도메인 원장. **예외: AML 탐지 기준은 A-Safe(외부), 이상탐지 룰은 FDS(기존 수행)/KFDS(신규 추가/수행), 쿠폰 정책은 KCPS — 아래 항목 참조.**
- **AML 탐지 기준은 외부 솔루션 A-Safe가 본체** — 정책=KOD 일반 원칙의 예외. **AMLS**는 A-Safe ↔ 코나 *중재 어댑터*(정책 본체 아님). AML 탐지 기준 변경 요건의 정책 본체는 우리 카탈로그 외부(A-Safe)에 있으며, AMLS는 새 기준 전달의 중재 어댑터로서 영향을 받음.
- **이상탐지 룰: FDS는 기존 수행 전용(룰 추가 불가), KFDS는 신규 룰 추가/수행** — 정책=KOD 일반 원칙의 예외. **FDS**는 기존 이상탐지를 수행만 하는 read-only 적용자(룰 추가 불가). **KFDS**는 신규 이상탐지 룰의 본체이자 수행자. 신규 이상탐지가 필요한 요건은 KFDS가 1차 영향, FDS는 영향 아님(룰 추가 안 함). 카탈로그상 KFDS 설명 "A-safe 대체"는 outdated/오류이지만 사용자 결정으로 유지.
- **쿠폰 정책은 KCPS가 본체** — 정책=KOD 일반 원칙의 예외. KCPS(KonaCard 쿠폰 시스템)가 외부/내부 쿠폰 발행/취소와 정책을 함께 들고 있다. 쿠폰 정책 변경 요건의 1차 영향은 KCPS, 다른 도메인 원장은 KCPS 정책을 받아 적용.
- **components.md 의존성 자동 보강은 차단** — 담당자도 전체 의존성 도식을 모른다. 위키, APIGW, Kafka, 소스 코드, 핀포인트, 입력 키워드 어떤 경로로도 자동 보강이 불가능함이 확인되었다. 보강 요청이 와도 "현재 시점 사실 + IMPACT-INDEX 누적" 외 방법은 없다 — 추측·역공학으로 채우지 말 것.
  - **IMPACT-INDEX의 실체**: 영향 분석 워크플로우(위 섹션) 매 호출마다 `impact_log.jsonl`에 한 라인씩 추가되는 누적 로그가 IMPACT-INDEX다. 즉 자동 의존성 추출이 아니라 **실제 요건 분석 이력의 누적**이 도식 보강의 유일한 합법 경로다. `impact.py`도, Claude Code 추론도 외부 시스템에서 정보를 끌어오지 않고 components.xlsx/components.md 내부 사실만 근거로 한다.
